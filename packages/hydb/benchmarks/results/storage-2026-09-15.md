# HyDB file vs LMDB benchmark — September 15, 2026

**LMDB improves batched writes and keeps reads/writes moving during GC, but its
current collector is slower overall and uses substantially more resident memory.**
These results support continuing the prototype, not switching the app default yet.

Storage implementation: `ac2e91f`. Apple M5, 10 logical CPUs, 32 GiB RAM,
macOS/Darwin 25.5.0, Node v24.19.0, LMDB 3.5.6, local data volume.
Three fresh-process repetitions per engine/dataset, alternating engine order.
All 12 runs passed full row verification before and after reopening.

## Reads and writes

Numbers below are medians of the three per-run measurements. Small rows carry
256-byte payloads (2,000 rows); large rows carry 16 KiB (256 rows). Both have one
secondary index. The scan datasets therefore contain about 0.49 MiB / 4 MiB of
payload. Write timings wait for durable acknowledgement.

| Measurement                        |  Small: file |  Small: LMDB | Large: file | Large: LMDB |
| ---------------------------------- | -----------: | -----------: | ----------: | ----------: |
| Single-row write p50               |      4.03 ms |      4.03 ms |     5.96 ms |     5.06 ms |
| Single-row write p95               |      5.03 ms |      5.15 ms |     9.02 ms |     7.10 ms |
| Single-row write throughput        |   236 rows/s |   233 rows/s |  162 rows/s |  179 rows/s |
| Batch write p50 (64 / 16 rows)     |     23.46 ms |     11.09 ms |    35.91 ms |    29.55 ms |
| Batch write throughput             | 2,571 rows/s | 5,530 rows/s |  435 rows/s |  527 rows/s |
| Warm point read p50                |         4 µs |         4 µs |       10 µs |       10 µs |
| HyDB-cache-disabled point read p50 |        53 µs |        28 µs |      935 µs |      748 µs |
| Full-table scan p50                |      2.16 ms |      2.13 ms |     2.08 ms |     2.00 ms |
| Indexed query p50                  |      1.14 ms |      1.14 ms |    0.245 ms |    0.239 ms |
| Reopen elapsed                     |      8.91 ms |      2.11 ms |     8.68 ms |     2.34 ms |

**Interpretation:** Small batches gain about **2.15× throughput**; large batches
gain about **1.21×**. Small single-row writes are effectively tied. Warm reads are
similar because both engines share the same HyDB tree/cache implementation.
Disabling HyDB's cache favors LMDB, but the OS cache was still warm.

## Garbage collection and foreground latency

Each GC run competed with 100 writes and 100 reads. GC duration and p95 values are
medians across runs; maxima are the **worst observation across all three runs**.

| Measurement                      | Small: file | Small: LMDB | Large: file | Large: LMDB |
| -------------------------------- | ----------: | ----------: | ----------: | ----------: |
| GC elapsed                       |     41.6 ms |    1,143 ms |     49.0 ms |      470 ms |
| Writes completed before GC ended |       0/100 |     100/100 |       0/100 |      35/100 |
| Reads completed before GC ended  |       0/100 |     100/100 |       0/100 |     100/100 |
| Worst write during GC workload   |     46.1 ms |     20.2 ms |     62.8 ms |     21.9 ms |
| Worst read during GC workload    |     42.0 ms |     1.16 ms |     56.4 ms |     1.46 ms |
| Write p95 without GC             |     5.88 ms |     5.88 ms |     6.07 ms |     6.84 ms |
| Write p95 with GC                |     6.04 ms |    12.43 ms |     7.86 ms |    14.94 ms |

The new collector eliminates the whole-cycle admission pause, but **does not make
GC free**. LMDB's per-batch contention roughly doubles write p95 here. The file
engine's p95 hides its single big initial pause; maximum latency exposes it.
LMDB's GC is approximately **27.5× slower for small rows and 9.6× for large rows**
in total elapsed time on these datasets. It also overlaps useful foreground work,
so elapsed GC duration is not a pure CPU comparison.

The work differs: file compaction copies only the retained pages using its commit
metadata, whereas the prototype scans all page keys **and payloads** and durably
publishes multiple delete batches. In the first small run, it deleted 15,673 pages;
the file collector copied 143 records. Large-run numbers were 3,966 deleted pages
versus 44 copied records. This is a concrete optimization opportunity in the KV
collector, not evidence that LMDB itself has inherently slow reclamation.

## Disk space and memory

Disk numbers are median **allocated MiB for the complete database directory**.
The second GC is quiescent and collects history created during the concurrent run.

| Disk stage                    | Small: file | Small: LMDB | Large: file | Large: LMDB |
| ----------------------------- | ----------: | ----------: | ----------: | ----------: |
| Before concurrent GC          |        96.8 |       106.1 |       651.0 |       654.6 |
| After concurrent GC + traffic |        3.44 |       106.1 |        78.9 |       670.6 |
| After second, quiescent GC    |        1.06 |       106.1 |        8.23 |       670.6 |
| After another 100 updates     |        3.44 |       106.1 |        78.9 |       670.6 |

**LMDB reclaimed reusable space, not filesystem space.** The next 100 updates
caused no measured file growth. The file engine shrank its files, then grew again.
A smaller LMDB file would require a separate compact-copy operation.

| Memory (median of per-run peaks) | Small: file | Small: LMDB | Large: file | Large: LMDB |
| -------------------------------- | ----------: | ----------: | ----------: | ----------: |
| OS peak RSS                      |     307 MiB |     460 MiB |     379 MiB |   1,323 MiB |
| Sampled JS heap peak             |      95 MiB |      98 MiB |     120 MiB |     151 MiB |

RSS includes resident mapped file pages, buffers and JS memory. These measurements
do not establish a memory leak or identify a single cause, but the large-value
RSS difference is significant. The prototype also stages/copies write batches and
reads full payloads during sweeping; those paths deserve profiling.

## What to improve next

1. **Avoid loading dead page payloads during sweep.** Add a bounded keys-only
   cursor and keep byte accounting separate from reclamation work.
2. **Measure and reduce memory use.** Profile mapped-page residency and duplicate
   buffers during batch construction/publication before choosing a larger workload.
3. **Tune GC scheduling and batch size against write p95/p99.** The current fixed
   128-record slices preserve progress but still materially delay commits.
4. **Reduce write amplification above the backend.** Both engines create hundreds
   of MiB while modifying only a few MiB of live rows. Changing the backend alone
   does not remove repeated tree-page/index rewrites.

These are synthetic, single-instance local results. They do not establish behavior
at the user's earlier 44 GB scale, with multiple processes, on cold storage or in
the cloud. Keep the app on its current backend until those questions are tested.
