# Where the LMDB prototype's memory goes

## Findings

The ~1.3 GiB RSS result has **two separate causes**:

1. The page sweep reads obsolete payloads and makes roughly **657 MiB of clean
   file-backed pages resident**. These pages count in RSS but are not private JS
   objects. Closing LMDB removes the mapping.
2. Write staging creates large temporary buffers. After those buffers die, the
   native allocator retains hundreds of MiB of fragmented/unused space. This is
   the more important private-memory problem.

There is no evidence in these runs of hundreds of MiB of permanently live JS
objects. That does not rule out every long-running leak.

[Raw measurements and vmmap summaries](memory-2026-09-15.json)

## Method

Engine code at `0d2fb64` (storage implementation unchanged from `ac2e91f`), same
Apple M5 / 32 GiB machine, Node 24.19.0, LMDB 3.5.6. Five isolated diagnostic
runs: original large-value workload on file and LMDB, the LMDB workload with an
experimental keys-only sweep, and two seed-only LMDB workloads with different
transaction sizes. Every workload validated its rows; the full workloads also
validated reopening. Production storage code was not changed.

Collected `process.memoryUsage()` throughout each phase and macOS `vmmap
-summary` snapshots at boundaries. Explicit JS GC runs only at diagnostic
checkpoints after cleanup/close. These instrumented runs are attribution probes,
not replacements for the earlier latency benchmark. There is one run per variant;
the original high-RSS behavior was already repeated three times and was reproduced
again here. vmmap snapshots can perturb timing and do not exactly coincide with
Node's preceding sample.

## 1. RSS and private memory tell different stories

After the main LMDB workload, a second database collection and explicit JS GC:

| Measurement                            |        LMDB | File engine |
| -------------------------------------- | ----------: | ----------: |
| RSS                                    | 1,289.3 MiB |   330.7 MiB |
| macOS physical footprint               |   615.4 MiB |   313.9 MiB |
| Resident `mapped file` regions         |   657.2 MiB | none listed |
| Live JS heap                           |    18.1 MiB |    12.1 MiB |
| V8 heap capacity (`heapTotal`)         |   150.0 MiB |   142.8 MiB |
| Node ArrayBuffer/Buffer bytes          |    16.5 MiB |    16.2 MiB |
| Native malloc zone resident            |   407.6 MiB |   106.3 MiB |
| Native malloc zone allocated           |    26.4 MiB |    22.4 MiB |
| Native malloc zone fragmentation/slack |   381.2 MiB |    83.9 MiB |

These rows are **overlapping accounting views**, not numbers to add together.
For example, Node's `arrayBuffers` is included in `external`, and allocations
already contribute to process memory. See [Node's definitions](https://nodejs.org/docs/latest-v24.x/api/process.html#processmemoryusage).

RSS includes clean mapped files; Apple's footprint accounting focuses on charged
dirty/compressed/swapped memory. This explains why RSS is much higher than the
footprint here. See [Apple's explanation of vmmap and footprint](https://developer.apple.com/videos/play/wwdc2022/10106/).

This refines the earlier comparison: **the footprint gap was about 301 MiB**, not
the entire ~959 MiB RSS gap at this checkpoint. Both are real measurements, but
they answer different questions. Clean file-backed pages are more readily
reclaimable than private allocations. [Apple virtual-memory overview](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/ManagingMemory/Articles/AboutMemory.html)

## 2. The collector unnecessarily brings obsolete data into RAM

Within the same LMDB run:

| Checkpoint         |         RSS | Resident mapped files | Physical footprint |
| ------------------ | ----------: | --------------------: | -----------------: |
| Before GC          |   806.1 MiB |             165.6 MiB |          623.7 MiB |
| After GC + traffic | 1,290.6 MiB |             657.2 MiB |          616.8 MiB |

RSS rose ~485 MiB, while the charged footprint actually fell slightly. The rise
tracks mapped-file residency, not growing live JS data.

Source path:

- `src/node/key-value-gc.ts` sweeps with `batches("page/")`.
- `src/node/lmdb-key-value-store.ts` uses `getRange`, retrieves each value and
  copies it with `Uint8Array.from(value)`.
- Large binary values are also copied by the installed LMDB binding's read path
  (`node_modules/lmdb/read.js`).
- Sweep only needs a page ID to decide whether the record is unmarked. Loading the
  dead payload serves the report's byte accounting, not the deletion decision.

**Controlled experiment:** replace only the page sweep's enumeration with LMDB
`getKeys`. The experimental adapter yields placeholder values, so its GC byte
report is deliberately invalid; it is diagnostic-only and not a production fix.
Actual commit/page deletion logic and verification remain in place.

| After GC + traffic    |    Original | Keys-only sweep |
| --------------------- | ----------: | --------------: |
| RSS                   | 1,290.6 MiB |       845.6 MiB |
| Resident mapped files |   657.2 MiB |       222.2 MiB |
| Physical footprint    |   616.8 MiB |       611.1 MiB |

This isolates roughly **435 MiB of avoidable mapped-page residency**. It does not
solve the private allocator footprint. Some pages remain resident because normal
reads, marking and writes still touch them.

## 3. Write amplification becomes memory amplification

The large benchmark has only **4 MiB of live row payload**. It seeds 64 rows per
transaction: 1 MiB of new row payload in each transaction. The isolated seed probe
measured up to **67.5 MiB of serialized put values in one publication batch**.

The relevant chain is:

1. `tree-storage-model.ts` applies row mutations individually.
2. `bplus-tree.ts` serializes a new immutable tree page for each change. Each page
   contains multiple rows, encoded as base64 strings inside JSON.
3. `key-value-pages.ts` keeps **every intermediate page** in its `pending` map,
   including versions superseded later within the same commit.
4. `key-value-store.ts: prepareBatch` clones each put value again to satisfy the
   backend's input-ownership contract.
5. The LMDB adapter calls `Buffer.from(op.value)` for each native put, making
   another copy. Reads into the tree also have ownership copies.

Some copies are contractually necessary today; removing them blindly risks
mutating queued writes or retaining unsafe native buffers. But staging all
intermediate tree versions and repeatedly copying them greatly amplifies a batch.
The file engine writes intermediate records as it goes; it has the same disk
amplification, but does not accumulate that entire publication batch in memory.

### Smaller-transaction experiment

Same 256 rows × 16 KiB, same index and page/cache settings, only seed transaction
size changes. This is diagnostic evidence, not a recommendation to silently split
application transactions and lose their atomicity.

| Seed-only probe                        | 64 rows/transaction | 8 rows/transaction |
| -------------------------------------- | ------------------: | -----------------: |
| Largest serialized publication         |            67.5 MiB |           10.3 MiB |
| RSS after close + explicit JS GC       |           594.9 MiB |          365.1 MiB |
| Physical footprint after close + JS GC |           574.1 MiB |          342.9 MiB |
| Native allocator fragmentation/slack   |           375.5 MiB |          152.3 MiB |
| Live JS heap after close + JS GC       |            10.5 MiB |           10.6 MiB |

Reducing the transient burst lowered residual footprint by about **231 MiB**,
without changing the final dataset. The 64-row seed alone reproduced most of the
original run's ~615 MiB private footprint.

## 4. Why JavaScript GC and close don't return all the RAM

After closing the full benchmark database and forcing JS GC:

- LMDB: RSS 632.4 MiB, footprint 615.5 MiB, live JS heap 11.5 MiB.
- File: RSS 330.9 MiB, footprint 314.2 MiB, live JS heap 12.0 MiB.
- The native malloc-zone resident difference was **301.3 MiB**, essentially the
  entire footprint difference at that checkpoint.

The JS objects/buffers were freed, but `vmmap` reports large unused/fragmented
areas remaining in the allocator's resident regions. Freeing an object does not
necessarily release its underlying allocator pages to the OS. V8 also retains
heap capacity beyond currently live objects. The measurements establish retained
allocator capacity/fragmentation; they do not establish that every byte can be
immediately released or predict behavior under sustained OS memory pressure.

## Recommended order

1. **Bound transaction staging without splitting atomic transactions.** Avoid
   retaining/serializing superseded intermediate pages; publish only pages
   reachable from the final transaction roots. Pruning only at the very end
   reduces writes but may not prevent the peak while building the transaction.
2. **Reduce redundant buffer copies through explicit ownership transfer.** Keep
   the swappable adapter's safety contract; consider a private owned-buffer path
   rather than weakening the public interface.
3. **Implement a real keys-only GC cursor.** Track sizes separately if needed;
   don't touch dead payloads just to report reclaimed bytes.
4. **Track footprint, buffers, heap and mapped residency separately** in future
   comparisons, and run a longer pressure/soak test after those changes.

The strongest finding is architectural: the prototype turns immutable-page write
amplification into a large temporary in-memory publication, then leaves allocator
slack behind. Switching away from LMDB would not address that write amplification.
