# First iteration: the document becomes the work

This iteration changes hyagent from a mock review surface into a small working agent
runtime. The defining shift is that the model no longer submits one complete document
at the end. It edits a live literate diff, and each accepted patch block is reflected
in the current repository worktree as the document develops.

## The agent has three tools

The model-facing interface is deliberately narrow:

```ts
read_file(repo, path);
run_command(repo, command, args);
edit_literate_diff(operations);
```

Reading and commands operate directly in a selected repository. Searching, tests,
builds, formatting, and generation remain ordinary commands rather than becoming a
validation framework.

`edit_literate_diff` is the only code-writing path. It can change the document summary,
insert or revise prose and diagrams, manipulate patch blocks, and maintain the visible
generated-file ignore footer. This keeps file mutation attached to the explanation
that justifies it.

The previous tool surface ended the turn with a complete replacement:

```diff
- submit_literate_diff(completeDocument)
+ edit_literate_diff(operations)
```

The custom loop now continues after each edit. Every edit becomes a hydb revision, so
the UI can display the overview before the patches and later patches before the agent
has finished its turn.

## Patch blocks now drive the worktree

A patch block names its repository and keeps a stable block ID:

```ts
{
  id: "add-session-loader",
  kind: "apply_patch",
  repository: "web",
  title: "Load the active session",
  rationale: "The thread and document need one shared source of truth.",
  patch: "...unified patch...",
}
```

The runtime compares the previous and next patch stacks for each repository. An
unchanged prefix stays applied. The changed suffix is reversed, the replacement is
applied, and later patches are replayed in order. If replay fails, the tool reports the
first failing block and restores the prior worktree state.

Repositories are independent at this mechanical level. One document can interleave
`web`, `api`, and `shared` patches into a coherent story, while revising a `web` patch
only replays the later `web` patches.

## Existing command changes can become documented changes

Commands sometimes write files before the agent has described those writes. When a
new patch already matches the worktree, the patch runtime can adopt it instead of
trying to apply the same change twice. This lets the agent run a formatter or generator
and then incorporate the meaningful result into the literate diff.

The runtime records a lightweight worktree snapshot at the beginning of the run. After
tools return, it compares the current Git-visible file state with the state accounted
for by accepted patch blocks. Unrecorded paths are returned to the model as a
`WORKTREE_INCONSISTENT` warning and are also persisted in the thread.

The agent can resolve a warning by adding the change to a patch or by acknowledging a
generated path. Acknowledged paths appear in the document footer:

```text
Generated artifacts not included

api/coverage/summary.json    Generated by the test suite
```

This is a literate-diff ignore, not a `.gitignore` mutation.

## Multi-repository work is explicit but small

The server accepts a JSON map of repository names to current worktrees:

```sh
HYAGENT_REPOSITORIES='{"web":"/projects/web","api":"/projects/api"}' \
  npm run dev:hyagent
```

Repository names flow through file reads, commands, patch blocks, worktree warnings,
generated ignores, and UI file headings. Hydb still stores one thread and one document.
No distributed commit protocol was added.

## The UI follows incremental revisions

While feedback is running, the browser subscribes to Hydb-backed session updates over
tRPC WebSockets and replaces the visible document as new revisions arrive. The follow
control keeps the active area in view. Patch headings include `repository/path`, and
generated ignores render as the final document section.

Acceptance does not reapply the patch set. By that point the patch stack is already
present in the current worktrees. Acceptance checks for unexplained changes, generates
a focused commit message for each affected repository, commits only document paths,
and records the resulting commit hashes.

## What remains intentionally primitive

This is enough to test the interaction, not a finished execution engine.

- The baseline and expected worktree snapshots live in the server process.
- Consistency checks cover tracked and non-ignored untracked Git paths; Git-ignored
  outputs are not discovered automatically yet.
- Commands are bounded to `rg`, read-only `git`, and `npm`.
- Cross-repository acceptance creates one commit per repository, but is not atomic
  across repositories.
- The patch replay implementation favors clarity over performance.

These limitations leave room to learn from the running agent before committing to a
more elaborate protocol.

## Evidence

The first iteration is covered by focused tests for:

1. document operations preserve stable blocks and generated ignores;
2. hydb stores incremental revisions;
3. the model loop publishes document edits before it stops;
4. patch replay, first-failure recovery, multi-repo isolation, and generated ignores
   work in temporary Git repositories; and
5. acceptance, AI commit messages, and path-scoped Git commits;
6. live Hydb subscriptions and activity ordering; and
7. persisted session switching and archiving.

The package passes TypeScript checking, its test suite, and the Vite production build.
The running server also responds successfully on `127.0.0.1:4328`, with the UI on
`127.0.0.1:5184`.
